## **Standard README Template**

### **Proposed Sections**

1. **Repository Name**
   - Clearly identify the repo.
2. **Plain-Language Purpose**
   - Define what this repository is for, in plain language.
3. **Current Status**
   - Specify whether it is experimental, active, deprecated, or paused.
4. **Intended Audience**
   - Identify who this README is written for (e.g., developers, contributors, general audience).
5. **What This Repo Contains**
   - Include an overview of primary files, folders, or functionality.
6. **Quick Start / How to Read This Repo**
   - Offer a simple introduction for new users — steps, examples, or usage notes.
7. **What Is Safe to Do**
   - Clarify any actions or experiments that can be run confidently.
8. **What Is Blocked or Not Active**
   - Highlight areas that are still in design, development, or paused.
9. **Relationship to SCOS**
   - Explain how this repository fits into the SCOS ecosystem if appropriate.
10. **Contribution / Collaboration Rules**
    - Define guidelines, procedures, or boundaries for contributors.
11. **License / Ownership Note**
    - Include applicable license details or ownership disclaimers.
12. **Next Recommended Action**
    - Direct readers toward the next steps or resources for more information.

---

## **SCOS Safety Language**

Every README should clearly separate these elements:

- **Verified Current Capability**: Describe features that are confirmed and tested.
- **Design Intent**: Highlight features that are planned.
- **Future Roadmap**: Outline the long-term plans or priorities.
- **Blocked Actions**: Specify activities that cannot be performed due to work-in-progress.
- **Runtime Status**: Avoid claims unless verified by active production readiness.
- **Contribution Boundaries**: Set clear expectations for outside collaboration.
